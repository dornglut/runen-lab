# Runtime comparison — Runen Lab #9

Independent Rust research project comparing a restricted generated **Typed Differential Execution (TDE)** candidate against **Bevy ECS 0.20.1** and the pinned accepted **RunenECS** public API.

This is a downstream experiment, not framework implementation authority. No performance or general-purpose superiority claim follows from the correctness oracle.

## Correctness experiment

- All three implementations receive the same staged transactions from `src/contract.rs`.
- `src/bevy_backend.rs` uses Bevy App, relationships, change detection, scheduling, and publication.
- `src/runen_backend.rs` uses RunenECS World, typed directed relations, queries, scheduling, and publication.
- `src/tde.rs` uses project-local reverse-index and packet-cache maintenance partly generated by `tools/compile_rule.py`.
- `src/main.rs` compares authoritative source state, derived packets, SHA-256 digests, versions, changed/removed identities, rejection outcomes, and epochs with **28,022** deterministic independent reference cases in `fixtures/`.

The TDE generator recognizes **one fixed foreign-key join schema**; it does not compile arbitrary Rust code or provide a general differential runtime. The shared admission path clones logical state: it is excluded from propagation-only timing and included in the separate transaction-mode measurement. This is not independent per-backend admission.

## Reproduce

From this project directory, with the selected Rust toolchain and Python 3:

```sh
python3 tools/compile_rule.py --check
cargo fmt --all -- --check
cargo test --all-targets --locked
cargo clippy --all-targets --locked -- -D warnings
cargo run --release --locked
```

## Exploratory same-host benchmark

**Two distinct timing modes:** `propagation` measures backend apply + derived publication using precomputed before/after states and dirty sets; `transaction` additionally includes shared `propose()` validation, authoritative-state copying, dirty-set construction, and data handoff on every update. Neither mode times input parsing, system setup, or correctness readback. Alternating A/B updates are checked against the same transaction semantics in both directions before timing.

Benchmarks cover noop scheduler baseline, one-object sparse edits, all-object dense changes, material fanout, and relation reassignment. They include a fourth, deliberately simple **full-recompute reference** (copying the complete state and rebuilding packets), which is not an ECS. No baseline or stage may be reported as a framework-wide ranking.

The exact-head GitHub workflow also compiles the Release binary and samples five deterministic workloads at 128 and 2,048 objects in both timing modes. It executes each backend in separate processes and rotates execution order over six rounds. The workflow archives raw CSV rows and OS/CPU/toolchain information. The summary reports separate median propagation-only and shared-admission transaction latency per update; neither represents a complete independently implemented application stack.

To reproduce manually after `cargo build --release --locked`:

```sh
python3 tools/run_benchmarks.py --binary target/release/runtime-comparison --output benchmark-raw.csv --rounds 6 --objects 128 2048
```

Both timed regions include backend mutation, native scheduling, index updates, and derived publication. Transaction mode includes shared admission and state cloning; propagation mode excludes them. Setup, input decoding, and correctness readback remain **excluded**. Setup time is measured separately. Memory fields are Linux process RSS at baseline/after setup and peak high-water mark; they are **not** precise per-backend allocation measurements. The `transaction` mode uses one common staging implementation, not an independently implemented backend admission path. A single GitHub-hosted machine, fixed schema, and this specialized application cannot establish general-purpose superiority. Repeated independent hosts, additional sizes, independently implemented admission, retained-memory, and developer coordination remain unresolved.

The repository-level `cargo validate` remains a separate required gate. A project-specific GitHub workflow runs this replay on the exact PR head; project validation integration is coordinated with Runen Lab draft PR #8 and must not overwrite that owner's independent work.

## Evidence and limitations

The fixtures were verified independently in Python; that is not Rust execution evidence. Real Rust correctness requires successful exact-head project tests and replay. The exploratory Release benchmark is implemented but does not yet establish a general comparison. Any future comparison must time equivalent operations on one host, include update propagation and publications, report memory and user-authored coordination, preserve native ECS capabilities, and retain raw measurements. This project must not be used as proof that TDE outperforms Bevy or RunenECS.
